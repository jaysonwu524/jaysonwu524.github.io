在要求租戶隔離的報告系統中，一名用戶即使持有有效的 Access Token，也具備報告讀取 Scope，仍然不能隨意訪問另一家機構的報告。

如果他把請求中的報告 ID 換成其他租戶的報告，而網關只檢查令牌和 Scope，請求仍可能通過入口。判斷它能否訪問具體報告，還需要知道報告屬於哪個租戶、用戶與報告有什麼關係，以及當前允許哪些操作。

因此，資源鑑權的設計需要同時回答：誰管理規則，誰作出授權決策，誰負責執行，以及這些環節依賴的數據有多新。

下面以一個多租戶報告系統為例，討論網關入口鑑權、集中式授權決策和服務本地執行。三者可以組合使用。

## 一、先區分令牌校驗、授權決策與權限執行

認證確認訪問者是誰；令牌校驗確認當前憑證是否可信；授權決策判斷訪問者能否操作某項資源；權限執行則負責在未獲授權時真正阻止訪問。

對於 JWT Access Token，資源服務器需要按配置驗證簽名、發行方、受眾和時間約束，不能只解碼後讀取用戶 ID。對於不透明令牌，則通常通過令牌內省或服務端狀態查詢判斷其是否有效。

即使 JWT 校驗通過，也不代表賬號此刻仍然可用、權限尚未被撤銷，更不代表用戶能訪問任意報告。令牌中的角色和 Scope 反映的是簽發時的授權信息；是否需要查詢當前狀態，取決於業務允許多長的失效窗口。

Spring Authorization Server 提供 OAuth 授權服務器與 OpenID Connect 相關能力，包括授權流程和令牌簽發。它與資源服務器承擔不同職責，不能把它直接等同於“每次業務請求都要調用的權限服務”。

在報告系統中，可以先區分兩類檢查：入口判斷請求是否具備進入報告服務的基本條件；業務服務判斷用戶是否能讀取這份報告，或審批它當前所處的流程節點。

## 二、網關：儘早攔截，但不要替業務猜權限

網關適合完成通用、低成本的入口檢查：驗證令牌，按路由檢查基礎 Scope 或角色，並按需要執行黑白名單、限流及賬號狀態檢查。這些能力可以在無效請求進入內部服務前將其攔截。

對於報告讀取請求，網關可以要求調用方具備 `report:read` Scope。但報告的所屬租戶、歸屬關係和審批狀態，通常仍由報告服務維護。如果網關為了判斷具體資源權限，反覆跨服務查詢這些信息，就會承擔越來越多的業務耦合與遠程調用成本。

網關擴容只能增加網關自身的處理能力。如果瓶頸是共享的權限數據庫或權限服務，增加網關實例甚至可能放大下游壓力。此時需要先區分瓶頸來自令牌計算、遠程查詢，還是業務權限模型，而不是直接把擴容當作通用答案。

另一個容易被忽略的問題是身份如何傳遞。業務服務不能直接信任客戶端提交的 `X-User-Id`、`X-Tenant-Id` 等請求頭。若採用網關身份轉發，必須移除或覆蓋外部同名字段，並讓服務能夠驗證身份信息的來源與完整性，例如通過經認證的內部通道或簽名斷言。

業務服務也可以重新校驗適用於自身的訪問令牌。無論選擇哪種方式，都應明確可信入口；“請求來自內網”本身不足以證明身份可信。繞過網關的 RPC、內部接口和任務入口，同樣需要適合其調用方式的身份與權限控制。

## 三、集中式決策：統一規則，同時承擔遠程依賴

當多個服務需要共享角色、組織關係或屬性規則時，可以引入獨立的權限服務或策略引擎。調用方提交主體、資源、操作及必要上下文，權限服務返回允許或拒絕，調用方據此執行。

例如，報告服務可以詢問：“用戶 A 能否審批租戶 T 的報告 R？”其中租戶、報告狀態和審批關係，應來自可信身份上下文或權威業務數據，不能直接採信請求中自報的屬性。

集中式決策有利於統一權限模型、複用規則和集中審計，但不會自動使數據保持最新：如果審批關係只緩存在權限服務中，仍要處理其更新與失效。將業務數據搬到中心服務，也會增加同步成本。

遠程決策還會引入網絡延遲和故障依賴。沒有獲得有效授權結果時，受保護的操作應默認拒絕。若允許複用已有緩存結果，就需要事先限定適用操作、有效期和撤銷生效窗口，不能在超時後臨時改為放行。

緩存鍵也不能只有用戶 ID。針對某份報告的決定，至少需要區分主體、租戶、資源和操作；如果決定依賴審批狀態或策略版本，這些依賴也需要進入緩存設計或失效條件。讀取被允許，不代表審批也被允許；一份報告的結果，也不能套用到另一份報告。

集中管理策略不等於每次請求都遠程決策。規則可以統一維護、按版本發佈到各服務，再結合本地業務數據執行。選擇遠程還是本地，取決於規則複雜度、數據歸屬與一致性要求。

## 四、服務本地執行：把權限落到具體資源與操作

業務服務最接近報告的所屬租戶、歸屬關係和流程狀態，適合執行資源級權限判斷。網關完成基礎檢查後，報告服務仍應確認“這名用戶能否讀取這份報告”。

下面是方法安全層的示意，`#p0` 表示第一個方法參數：

```java
@PreAuthorize("@reportPermission.canRead(authentication, #p0)")
public ReportDetail getReportDetail(Long reportId) {
    return reportService.getDetail(reportId);
}
```

這裡的關鍵是 `canRead` 的實際實現。它需要從可信身份上下文獲取用戶與租戶，查詢報告的權威歸屬關係，並按規則判斷讀取權限。註解本身不會自動提供這些業務語義。

在 Spring Security 中，還需要啟用方法安全，並確認調用經過相應代理。默認的代理模式下，同類自調用可能繞過攔截；未受保護的方法也不會因為項目裡存在鑑權註解就自動安全。因此，應檢查所有可達入口，而不是隻給某個 Controller 加切面。

數據查詢同樣需要落實權限範圍。報告列表不能先查詢全部數據，再僅靠前端隱藏無權查看的條目；查詢、分頁計數和導出都應使用相應的租戶與數據權限條件。

對於審批等寫操作，還要考慮檢查與執行之間的狀態變化：檢查時用戶仍是審批人，提交時報告卻可能已經進入下一節點。相關流程狀態和審批資格如果存儲在同一業務庫中，需要把校驗與更新納入同一原子邊界，例如在適當鎖定後校驗，或執行包含相關狀態、版本條件的原子更新。僅開啟事務並不自動消除競態。若依賴跨服務狀態，則還需要明確協調邊界，單靠前置註解不能保證執行時條件仍然成立。

本地執行會讓鑑權工作隨業務請求分散，但負載是否均衡仍取決於實際流量。它也要求各服務使用一致的規則定義，並覆蓋各自的訪問入口。

## 五、權限撤銷：先定義生效窗口，再選擇同步機制

“權限變更立即生效”需要進一步澄清：是變更確認後的新請求必須拒絕，還是已經開始的操作也要終止？對報告預覽、文件導出和審批提交，答案可能不同。

如果普通讀取允許一個明確的短暫窗口，可以使用有界緩存和事件失效。如果敏感操作要求撤銷確認後的新請求不得再使用舊權限，則必須在決策路徑上讀取足夠新的授權狀態，或使用能滿足該約束的版本校驗與同步確認機制；無法確認時拒絕執行。只縮短緩存 TTL，或發送一條“刷新緩存”通知，都不足以保證這一點。

策略同步也不能只考慮消息成功送達的情況。實例可能離線、錯過通知，或收到亂序更新。可以為策略分配單調遞增的版本，忽略舊版本覆蓋；實例啟動或重連時重新拉取當前版本，並通過週期性核對發現漏更。

版本號能夠幫助識別差異，不能讓所有節點自動同時生效。對於要求協調切換的策略，需要等待相關實例確認或限制未同步實例繼續處理相應請求；如果允許短暫不一致，則應明確最長窗口，並監控各實例版本的落後情況。

## 六、如何組合，而不是三選一

三種方式關注的位置不同：

| 方式 | 主要職責 | 適合解決的問題 | 必須承擔的代價 |
| --- | --- | --- | --- |
| 網關入口鑑權 | 令牌與基礎路由權限檢查 | 儘早攔截無效請求，統一入口規則 | 業務上下文有限，遠程查詢可能拖慢入口 |
| 集中式授權決策 | 跨服務規則的統一判斷 | 共享權限模型與策略 | 網絡依賴、中心容量、數據新鮮度與決策緩存 |
| 服務本地執行 | 結合業務數據檢查資源與操作權限 | 租戶隔離、資源歸屬、流程權限 | 檢查覆蓋、規則同步，以及檢查與執行的協調 |

在這個報告系統的示例中，可以採用以下組合：

```text
請求
  → 網關：校驗令牌與報告讀取 / 審批 Scope
  → 報告服務：驗證身份上下文，檢查租戶、資源與操作權限
      ├─ 本地業務數據 + 已同步策略
      └─ 必要時請求集中式權限服務
  → 獲得有效授權後讀取或提交，並記錄必要的審計信息
```

選型時，先明確權限粒度、撤銷生效窗口和故障時的處理要求，再比較額外延遲、吞吐、可用性與維護成本。上線後，應觀察授權耗時、遠程決策超時率、緩存命中率和策略版本落後情況；緩存命中率很高，也可能意味著權限變更遲遲沒有生效，需要結合一致性指標判斷。

合理的分工，是讓入口檢查保持通用，讓資源權限靠近業務，讓需要共享的策略能夠統一維護。規則在哪裡管理、決策在哪裡計算、結果在哪裡執行，可以分別選擇，但它們之間的身份、數據與故障邊界必須清楚。
