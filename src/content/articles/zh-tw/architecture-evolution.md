子公司成立於 2023 年 6 月。我在 8 月到崗時，研發以項目制推進：不同項目從已有倉庫複製代碼，各自維護部署環境，也各自連接行情供應商。

當時採購的部分 Twelvedata、Finnhub 套餐，將單個 API Key 的 WebSocket 連接數限制在 1 到 3 條。業務尚未形成規模，重複接入卻已經帶來接近每月 2,000 美元的數據源成本。這是當時套餐與接入方式下的情況，並非供應商所有產品的固定限制。

RateHub 因此被設計為統一行情服務：集中接入 Twelvedata、Finnhub、Binance、XChange、SSI、Whitezzzs 等行情來源，管理 ETF、指數、股票、外匯、現貨及合約等標的，向下遊提供報價、盤口與多週期 K 線。

項目經歷了兩次架構選擇。第一版將接入與分發拆開，以 MongoDB 共享最新狀態；第二版將核心進程收斂，把最新行情放入 JVM 內存，直接從上游消息觸發推送。關鍵變化在於實時數據如何流動。

### 統一接入之外，還要提供可複用的數據接口

多個項目共用上游連接，只解決了重複接入的一部分問題。下游還需要通過同一套接口訂閱行情、展示漲跌幅，並查詢不同週期的 K 線，否則每個業務項目仍然需要自行適配供應商的返回格式。

| 能力 | 對下游提供的內容 |
| --- | --- |
| 實時訂閱 | 通過 WebSocket 向多個業務項目推送報價與日漲跌幅 |
| 最新 K 線更新 | 持續更新分鐘 K 線，供客戶端刷新當前週期的圖表 |
| 歷史 K 線查詢 | 統一查詢分鐘、日、周、月等週期的數據，並整理返回格式 |
| 多來源適配 | 將不同來源的接入與數據處理集中到行情服務，減少業務側重複適配 |

統一接口需要明確數據含義，不能只統一字段名稱。同一標的在不同來源中的代碼、價格單位、時間戳和週期邊界可能不同；當前分鐘 K 線也會繼續變化，不能把每次推送都當作新增一根已收盤 K 線。這些差異是接入與下游使用之間需要明確的約定。

行情還會成為交易業務的輸入。例如，下游在收到更新後檢查限價訂單、計算持倉風險，再按自身規則決定是否執行交易處理。RateHub 負責提供行情，訂單狀態、賬戶計算與結算由業務系統負責。展示最新快照的容錯要求，也不能直接作為資金結算的數據保證；一旦用於交易判斷，還需要在業務側明確來源、鮮度及異常行情的處理方式。

## 一、第一版：用共享數據庫連接接入與分發

第一版基於 JDK 17、Spring Boot、MongoDB、Redis、Kafka、XXL-Job 等組件構建。核心分為兩個角色：

| 角色 | 主要職責 | 部署考慮 |
| --- | --- | --- |
| Connect / 接入層 | 連接上游，接收報價並更新 MongoDB | 按上游連接與訂閱規模擴容 |
| Share / 分發層 | 管理鑑權與訂閱，查詢最新行情後通過 WebSocket 推送 | 按下游連接與推送負載擴容 |
| 任務處理 | 調度 K 線相關任務，用 Redis / Redisson 協調執行 | 避免同一任務併發重複處理 |

MongoDB 提供跨服務共享狀態，使分發實例能夠讀取接入層寫入的數據，而不必訪問其他實例的本地內存。

```text
上游 WebSocket → 接入服務 → MongoDB 最新行情
                                ↓ 定時查詢
                            分發服務 → 下游 WebSocket
```

最新報價採用按標的覆蓋更新的方式，控制記錄數量。但記錄數量有限，並不意味著讀寫成本有限；每次更新仍然需要數據庫處理，查詢和推送仍然持續發生。

行情鍵也需要限定作用域。同名交易對可能來自不同平臺或產品類型；K 線的唯一標識則需要包含數據源、標的、週期與起始時間。只用交易對文本或時間戳，無法在共享命名空間中區分這些數據。

這一版中的 Kafka 主要承擔監控事件和服務間通知。例如，接入服務發佈 WebSocket 連接狀態，管理服務異步消費、寫入 MongoDB，再推送到管理端。它沒有成為每條報價必經的廣播總線，因此也沒有替代實時報價中的數據庫中轉。

共享數據庫減少了各實例分別持有狀態的協調工作，但不會自動保證所有讀者在同一時刻看到同一個值。讀取時機、部署配置與更新順序，仍會影響實際可見狀態。

## 二、兩條壓力鏈路：行情讀寫與 K 線等待

第一條壓力來自報價的高頻讀寫。接入端持續更新，分發端按客戶端訂閱定時查詢。同一份行情可能因多個客戶端訂閱而被重複讀取。

```text
一次報價更新 → 數據庫寫入
                 → 按訂閱查詢一次或多次
                 → 推送到多個連接
```

這使讀取負載同時受到行情量和客戶端數量影響。即使行情暫時不變，定時輪詢與任務掃描仍可能製造 I/O。低業務量時觀察到高 I/O，需要結合慢查詢、掃描和任務頻率定位，不能僅憑現象認定是 MongoDB 的固有問題。

第二條壓力來自 K 線查詢與補數。上游 HTTP 響應變慢時，同步調用會佔用平臺線程等待；請求繼續進入，則連接池、線程池與隊列逐步積壓，最終拖慢其他請求。

兩條鏈路需要分別處理：減少最新行情對數據庫的反覆讀寫，調整 K 線任務的等待方式與併發規模。單純增加服務實例，仍可能把更多請求壓到同一數據庫或上游接口。

在這個服務的業務範圍內，下游需要的是最新快照與一定頻率的更新，不要求逐條重放所有報價。因此，最新狀態可以重新從上游建立。若用途變為逐筆回放、審計或精確重建行情，數據保留策略就需要重新設計。

## 三、第二版：把實時路徑收斂到一個進程

第二版採用 JDK 21、Spring Boot、Netty、MySQL、Redis、Kafka 等組件，將連接、行情狀態、訂閱管理和分發收斂到一個可獨立部署的應用。數據庫與消息系統仍是外部基礎設施。

上游回調收到報價後，直接觸發下游分發，並維護內存中的最新快照。新客戶端訂閱時，可以讀取已有快照。邏輯上的路徑縮短為：

```text
上游 WebSocket → 進程內行情處理
                   ├─ 更新最新快照
                   └─ 按訂閱推送 → 下游 WebSocket
```

這兩個分支都不需要先寫 MongoDB、再等待分發服務輪詢。移除網絡往返和數據庫中轉，直接減少了熱路徑的工作量；具體延遲與吞吐收益仍應由同條件測量確認。

最新行情按“平臺 + 標的”保存在 JVM 緩存中。接入多個平臺增加了來源選擇，但不同來源的同名資產、報價單位和合約定義未必等價。多源接入本身不提供自動故障切換；若要切換，需要明確標的映射、來源優先級、鮮度要求和對下游的通知方式。

Redis 定期保存報價與盤口快照，用於重啟時恢復最近狀態。恢復快照能夠縮短空白期，卻不能證明報價仍然新鮮，更不能補回所有漏掉的更新。對鮮度敏感的調用，應根據來源時間與本地接收時間判斷是否過期，待上游重新同步後再恢復正常可用狀態。

MySQL 承擔標的、授權等長期業務數據。K 線查詢則按需調用上游 API，並複用 Redis 中的時間區間緩存；這條查詢路徑並不依賴本地 MySQL 中存在一份完整的歷史行情檔案。

### Netty 解決連接模型，不提供固定容量保證

選擇 Netty，是為了用事件驅動模型管理長連接和異步分發。Tomcat 的實際連接容量同樣受協議實現、配置、操作系統與業務處理方式影響，不能簡單歸結為一個固定的 WebSocket 上限。

Netty 也不允許在事件循環中隨意執行慢 HTTP、阻塞鎖或重計算。慢客戶端還可能使發送緩衝持續增長。後續容量治理需要覆蓋連接數、待發送字節、事件循環延遲和客戶端消費速度。

如果下游只需要最新報價，可以評估合併尚未發送的舊快照；盤口增量則可能依賴順序與序列號，不能套用相同的丟棄策略，失序後可能需要重新獲取完整快照。

## 四、K 線：排隊、緩存與虛擬線程各自解決什麼

客戶端通過 WebSocket 請求 K 線時，處理器將請求寫入 `socket-candlestick-topic`，消費者執行上游查詢、緩存處理、去重、校驗和結果推送。週期性 K 線、迷你 K 線與漲幅任務，也由定時調度發佈消息，再異步執行。

Kafka 在這裡將慢任務移出 WebSocket 事件處理流程，並吸收短時突發。它不會增加上游 API 的額度；持續進入的任務超過消費能力時，等待只會轉移到隊列。因此，生產端發送的等待行為也要檢查，不能僅因調用了 Kafka 就斷言事件循環一定不會阻塞。

週期任務使用虛擬線程併發處理多個標的，降低可卸載的 I/O 等待對平臺線程的佔用。但 JDK 21 中仍存在 `synchronized` 等場景下的線程固定，不能理解為所有阻塞都會釋放載體線程。虛擬線程也不增加帶寬、連接池容量或上游限額，仍需要限制在途請求、設置超時，並控制重試退避。

K 線服務會複用已有時間區間緩存，再請求缺少的範圍，並處理重複時間戳與連續性。緩存和排隊仍有各自的正確性條件：

- 緩存鍵應能區分數據源、標的與週期，未收盤 K 線需要允許刷新；
- 股票等市場存在休市與交易時段，不能統一按連續的自然時間軸認定缺數；
- 周、月、年等日曆週期需要明確時區與邊界，不能都當成固定毫秒長度；
- 開收盤價修正應有明確業務定義。不同週期之間的跳空可能是真實行情，不能僅為畫面連續而覆蓋原始值。

這些條件決定了“緩存中有數據”是否等於“可以回答這次查詢”，也說明報價快照與歷史 K 線不能共用一套簡單的生命週期規則。

## 五、隊列治理：意圖不等於已經實現的能力

項目曾加入一個定期治理 K 線主題的任務，意圖是在規模超過閾值時刪除主題。但復盤實現時可以看到，所計算的是分區副本數與同步副本數的組合，而不是消息條數或消費者積壓。它不能證明系統已經具備可靠的積壓保護。

真正評估積壓，需要針對目標消費組比較分區末端偏移量與已提交偏移量，並觀察最老任務的等待時間。如果消費者很早提交、再異步處理任務，還要單獨統計進程內未完成工作。

刪除主題會丟失尚未處理的請求，並影響正在使用該主題的生產者與消費者。即使 K 線查詢可重試，也需要讓客戶端知道本次請求未完成，而不能把清理主題當成常規削峰策略。

更可控的演進方向，是按請求期限拒絕過期任務、限制接入與消費併發、合併重複查詢，並明確重試與失敗反饋。WebSocket 請求還需要關聯請求 ID 和有效連接；客戶端斷開後，任務完成也不代表結果已經交付。

## 六、收斂後的收益與新的邊界

兩版的核心差異可以概括為：

| 關注點 | 第一版 | 第二版 |
| --- | --- | --- |
| 最新報價共享 | MongoDB 更新與輪詢 | JVM 最新狀態與回調分發 |
| 慢任務處理 | 與線程資源競爭的同步請求 | Kafka 排隊，週期任務使用虛擬線程 |
| 重啟後的狀態 | 讀取共享存儲 | 恢復 Redis 快照，再重新同步上游 |
| 主要代價 | 實時數據庫 I/O、服務協調 | 單進程故障範圍、狀態恢復與容量控制 |

單進程減少了實例間同步最新行情的需要，也擴大了一次進程故障對接入與分發的共同影響。Redis 快照不會自動複製 WebSocket 連接，也不會使兩個實例擁有一致的訂閱與發送狀態。將來部署多個活躍實例時，仍需解決上游連接分配、訂閱歸屬、狀態同步及重連恢復。

後續是否拆分，應結合報價鮮度、推送延遲、事件循環延遲、發送積壓、內存、上游錯誤率和恢復耗時判斷。可用性目標也可能在容量耗盡之前，就要求冗餘部署與故障隔離。

RateHub 的收斂，首先解決了當時實時鏈路中不必要的共享存儲與輪詢。下一次演進則需要回答新的約束：哪一部分必須獨立擴容，哪些狀態需要冗餘，以及失敗後允許多長時間恢復。架構選擇的價值，在於這些問題有可以驗證的答案。
