子公司成立于 2023 年 6 月。我在 8 月到岗时，研发以项目制推进：不同项目从已有仓库复制代码，各自维护部署环境，也各自连接行情供应商。

当时采购的部分 Twelvedata、Finnhub 套餐，将单个 API Key 的 WebSocket 连接数限制在 1 到 3 条。业务尚未形成规模，重复接入却已经带来接近每月 2,000 美元的数据源成本。这是当时套餐与接入方式下的情况，并非供应商所有产品的固定限制。

RateHub 因此被设计为统一行情服务：集中接入 Twelvedata、Finnhub、Binance、Whitezzzs 等平台，管理 ETF、指数、股票、外汇、现货及合约等标的，向下游提供报价、盘口与多周期 K 线。

项目经历了两次架构选择。第一版将接入与分发拆开，以 MongoDB 共享最新状态；第二版将核心进程收敛，把最新行情放入 JVM 内存，直接从上游消息触发推送。关键变化在于实时数据如何流动。

## 一、第一版：用共享数据库连接接入与分发

第一版基于 JDK 17、Spring Boot、MongoDB、Redis、Kafka、XXL-Job 等组件构建。核心分为两个角色：

| 角色 | 主要职责 | 部署考虑 |
| --- | --- | --- |
| Connect / 接入层 | 连接上游，接收报价并更新 MongoDB | 按上游连接与订阅规模扩容 |
| Share / 分发层 | 管理鉴权与订阅，查询最新行情后通过 WebSocket 推送 | 按下游连接与推送负载扩容 |
| 任务处理 | 调度 K 线相关任务，用 Redis / Redisson 协调执行 | 避免同一任务并发重复处理 |

MongoDB 提供跨服务共享状态，使分发实例能够读取接入层写入的数据，而不必访问其他实例的本地内存。

```text
上游 WebSocket → 接入服务 → MongoDB 最新行情
                                ↓ 定时查询
                            分发服务 → 下游 WebSocket
```

最新报价采用按标的覆盖更新的方式，控制记录数量。但记录数量有限，并不意味着读写成本有限；每次更新仍然需要数据库处理，查询和推送仍然持续发生。

行情键也需要限定作用域。同名交易对可能来自不同平台或产品类型；K 线的唯一标识则需要包含数据源、标的、周期与起始时间。只用交易对文本或时间戳，无法在共享命名空间中区分这些数据。

这一版中的 Kafka 主要承担监控事件和服务间通知。例如，接入服务发布 WebSocket 连接状态，管理服务异步消费、写入 MongoDB，再推送到管理端。它没有成为每条报价必经的广播总线，因此也没有替代实时报价中的数据库中转。

共享数据库减少了各实例分别持有状态的协调工作，但不会自动保证所有读者在同一时刻看到同一个值。读取时机、部署配置与更新顺序，仍会影响实际可见状态。

## 二、两条压力链路：行情读写与 K 线等待

第一条压力来自报价的高频读写。接入端持续更新，分发端按客户端订阅定时查询。同一份行情可能因多个客户端订阅而被重复读取。

```text
一次报价更新 → 数据库写入
                 → 按订阅查询一次或多次
                 → 推送到多个连接
```

这使读取负载同时受到行情量和客户端数量影响。即使行情暂时不变，定时轮询与任务扫描仍可能制造 I/O。低业务量时观察到高 I/O，需要结合慢查询、扫描和任务频率定位，不能仅凭现象认定是 MongoDB 的固有问题。

第二条压力来自 K 线查询与补数。上游 HTTP 响应变慢时，同步调用会占用平台线程等待；请求继续进入，则连接池、线程池与队列逐步积压，最终拖慢其他请求。

两条链路需要分别处理：减少最新行情对数据库的反复读写，调整 K 线任务的等待方式与并发规模。单纯增加服务实例，仍可能把更多请求压到同一数据库或上游接口。

在这个服务的业务范围内，下游需要的是最新快照与一定频率的更新，不要求逐条重放所有报价。因此，最新状态可以重新从上游建立。若用途变为逐笔回放、审计或精确重建行情，数据保留策略就需要重新设计。

## 三、第二版：把实时路径收敛到一个进程

第二版采用 JDK 21、Spring Boot、Netty、MySQL、Redis、Kafka 等组件，将连接、行情状态、订阅管理和分发收敛到一个可独立部署的应用。数据库与消息系统仍是外部基础设施。

上游回调收到报价后，直接触发下游分发，并维护内存中的最新快照。新客户端订阅时，可以读取已有快照。逻辑上的路径缩短为：

```text
上游 WebSocket → 进程内行情处理
                   ├─ 更新最新快照
                   └─ 按订阅推送 → 下游 WebSocket
```

这两个分支都不需要先写 MongoDB、再等待分发服务轮询。移除网络往返和数据库中转，直接减少了热路径的工作量；具体延迟与吞吐收益仍应由同条件测量确认。

最新行情按“平台 + 标的”保存在 JVM 缓存中。接入多个平台增加了来源选择，但不同来源的同名资产、报价单位和合约定义未必等价。多源接入本身不提供自动故障切换；若要切换，需要明确标的映射、来源优先级、鲜度要求和对下游的通知方式。

Redis 定期保存报价与盘口快照，用于重启时恢复最近状态。恢复快照能够缩短空白期，却不能证明报价仍然新鲜，更不能补回所有漏掉的更新。对鲜度敏感的调用，应根据来源时间与本地接收时间判断是否过期，待上游重新同步后再恢复正常可用状态。

MySQL 承担标的、授权等长期业务数据。K 线查询则按需调用上游 API，并复用 Redis 中的时间区间缓存；这条查询路径并不依赖本地 MySQL 中存在一份完整的历史行情档案。

### Netty 解决连接模型，不提供固定容量保证

选择 Netty，是为了用事件驱动模型管理长连接和异步分发。Tomcat 的实际连接容量同样受协议实现、配置、操作系统与业务处理方式影响，不能简单归结为一个固定的 WebSocket 上限。

Netty 也不允许在事件循环中随意执行慢 HTTP、阻塞锁或重计算。慢客户端还可能使发送缓冲持续增长。后续容量治理需要覆盖连接数、待发送字节、事件循环延迟和客户端消费速度。

如果下游只需要最新报价，可以评估合并尚未发送的旧快照；盘口增量则可能依赖顺序与序列号，不能套用相同的丢弃策略，失序后可能需要重新获取完整快照。

## 四、K 线：排队、缓存与虚拟线程各自解决什么

客户端通过 WebSocket 请求 K 线时，处理器将请求写入 `socket-candlestick-topic`，消费者执行上游查询、缓存处理、去重、校验和结果推送。周期性 K 线、迷你 K 线与涨幅任务，也由定时调度发布消息，再异步执行。

Kafka 在这里将慢任务移出 WebSocket 事件处理流程，并吸收短时突发。它不会增加上游 API 的额度；持续进入的任务超过消费能力时，等待只会转移到队列。因此，生产端发送的等待行为也要检查，不能仅因调用了 Kafka 就断言事件循环一定不会阻塞。

周期任务使用虚拟线程并发处理多个标的，降低可卸载的 I/O 等待对平台线程的占用。但 JDK 21 中仍存在 `synchronized` 等场景下的线程固定，不能理解为所有阻塞都会释放载体线程。虚拟线程也不增加带宽、连接池容量或上游限额，仍需要限制在途请求、设置超时，并控制重试退避。

K 线服务会复用已有时间区间缓存，再请求缺少的范围，并处理重复时间戳与连续性。缓存和排队仍有各自的正确性条件：

- 缓存键应能区分数据源、标的与周期，未收盘 K 线需要允许刷新；
- 股票等市场存在休市与交易时段，不能统一按连续的自然时间轴认定缺数；
- 周、月、年等日历周期需要明确时区与边界，不能都当成固定毫秒长度；
- 开收盘价修正应有明确业务定义。不同周期之间的跳空可能是真实行情，不能仅为画面连续而覆盖原始值。

这些条件决定了“缓存中有数据”是否等于“可以回答这次查询”，也说明报价快照与历史 K 线不能共用一套简单的生命周期规则。

## 五、队列治理：意图不等于已经实现的能力

项目曾加入一个定期治理 K 线主题的任务，意图是在规模超过阈值时删除主题。但复盘实现时可以看到，所计算的是分区副本数与同步副本数的组合，而不是消息条数或消费者积压。它不能证明系统已经具备可靠的积压保护。

真正评估积压，需要针对目标消费组比较分区末端偏移量与已提交偏移量，并观察最老任务的等待时间。如果消费者很早提交、再异步处理任务，还要单独统计进程内未完成工作。

删除主题会丢失尚未处理的请求，并影响正在使用该主题的生产者与消费者。即使 K 线查询可重试，也需要让客户端知道本次请求未完成，而不能把清理主题当成常规削峰策略。

更可控的演进方向，是按请求期限拒绝过期任务、限制接入与消费并发、合并重复查询，并明确重试与失败反馈。WebSocket 请求还需要关联请求 ID 和有效连接；客户端断开后，任务完成也不代表结果已经交付。

## 六、收敛后的收益与新的边界

两版的核心差异可以概括为：

| 关注点 | 第一版 | 第二版 |
| --- | --- | --- |
| 最新报价共享 | MongoDB 更新与轮询 | JVM 最新状态与回调分发 |
| 慢任务处理 | 与线程资源竞争的同步请求 | Kafka 排队，周期任务使用虚拟线程 |
| 重启后的状态 | 读取共享存储 | 恢复 Redis 快照，再重新同步上游 |
| 主要代价 | 实时数据库 I/O、服务协调 | 单进程故障范围、状态恢复与容量控制 |

单进程减少了实例间同步最新行情的需要，也扩大了一次进程故障对接入与分发的共同影响。Redis 快照不会自动复制 WebSocket 连接，也不会使两个实例拥有一致的订阅与发送状态。将来部署多个活跃实例时，仍需解决上游连接分配、订阅归属、状态同步及重连恢复。

后续是否拆分，应结合报价鲜度、推送延迟、事件循环延迟、发送积压、内存、上游错误率和恢复耗时判断。可用性目标也可能在容量耗尽之前，就要求冗余部署与故障隔离。

RateHub 的收敛，首先解决了当时实时链路中不必要的共享存储与轮询。下一次演进则需要回答新的约束：哪一部分必须独立扩容，哪些状态需要冗余，以及失败后允许多长时间恢复。架构选择的价值，在于这些问题有可以验证的答案。
