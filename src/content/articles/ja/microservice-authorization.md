テナント分離が必要なレポートシステムでは、有効なアクセストークンと閲覧 Scope があっても、他の組織のレポートを自由に閲覧することはできません。

利用者が別テナントのレポート ID に置き換えても、トークンと Scope だけを調べるゲートウェイなら、要求は入口を通るかもしれません。特定のレポートへアクセスできるかは、所属テナント、利用者との関係、実行する操作にも依存します。

認可の設計では、誰がルールを管理し、誰が判断し、誰が適用するのか、そして判断に使うデータがどれほど新しいかを決める必要があります。

マルチテナントのレポートシステムを例に、入口検査、集中型の認可判断、サービス内での適用を考えます。これらは組み合わせて使えます。

## 1. トークン検証・認可判断・適用を区別する

認証はアクセスする主体を確認し、トークン検証は資格情報を信頼できるか確かめます。認可判断は特定のリソースへの操作を許可できるかを決め、その適用は許可のないアクセスを実際に阻止します。

JWT アクセストークンでは、リソースサーバーが設定に従って署名、発行者、対象、有効期間の条件を検証します。デコードして利用者 ID を読むだけでは不十分です。不透明なトークンでは、通常、イントロスペクションやサーバー側の状態照会で有効性を判断します。

JWT の検証成功は、現在もアカウントが有効で、権限が失効しておらず、どのレポートにもアクセスできることを意味しません。役割や Scope は発行時点の認可情報です。現在の状態を照会する必要性は、業務が許容する失効反映時間によります。

Spring Authorization Server は OAuth の認可フロー、トークン発行、OpenID Connect 関連の機能を提供します。リソースサーバーとは役割が異なり、すべての業務要求が呼び出す認可サービスと同一ではありません。

レポートサービスへ入る基本条件と、特定のレポートを読めるか、現在の承認段階で承認できるかは分けて考えます。

## 2. ゲートウェイ：早く拒否し、業務権限を推測しない

ゲートウェイは共通で低コストの入口検査に向いています。トークンを検証し、ルートごとに基本的な Scope や役割を確認し、必要に応じて許可・拒否リスト、レート制限、アカウント状態の検査を行います。無効な要求を内部サービスへ届く前に止められます。

閲覧要求なら `report:read` Scope を必須にできます。一方、レポートのテナント、所有関係、承認状態は通常レポートサービスが管理します。特定リソースの認可のために毎回サービスを横断して照会すると、入口に業務上の結合とリモート呼び出しのコストが集まります。

ゲートウェイの増設で増えるのは、その処理能力です。共有の権限 DB や認可サービスが制約なら、増設によって下流の負荷が増すこともあります。トークン処理、遠隔照会、権限モデルのどこがボトルネックなのかを先に区別します。

本人情報の伝達にも注意が必要です。業務サービスは、クライアントが送った `X-User-Id` や `X-Tenant-Id` をそのまま信用できません。ゲートウェイで転送するなら、外部の同名項目を削除または上書きし、認証済みの内部通信路や署名付きアサーションなどで、情報の出所と完全性を検証できるようにします。

サービス自身が、自身向けのアクセストークンを再検証する方法もあります。どちらでも信頼する入口を明確にする必要があり、内部ネットワークからの要求というだけでは本人確認になりません。ゲートウェイを通らない RPC、内部 API、ジョブ入口にも、それぞれの呼び出し方式に合った認証・認可が必要です。

## 3. 集中判断：共通ルールとリモート依存を引き受ける

複数サービスが役割、組織関係、属性ルールを共有するなら、独立した認可サービスやポリシーエンジンで判断できます。呼び出し元が主体、リソース、操作、必要な文脈を渡し、許可・拒否を受け取って適用します。

例えばレポートサービスは「利用者 A はテナント T のレポート R を承認できるか」と照会できます。テナント、レポート状態、承認関係は、信頼できる認証コンテキストや正規の業務データから取得し、要求の自己申告をそのまま使わないようにします。

集中判断はモデル統一、ルール再利用、監査集約に役立ちますが、データを自動で最新にするわけではありません。認可サービスが承認関係をキャッシュしているなら、その更新と無効化も必要です。業務データを集約するほど同期の負担が増えます。

リモート判断には通信遅延と障害依存も生じます。有効な認可結果を得られない保護対象操作は原則拒否します。キャッシュ結果の再利用を認めるなら、対象操作、有効期間、失効反映時間を事前に決め、タイムアウトを理由にその場で許可へ切り替えないようにします。

キャッシュキーを利用者 ID だけにすることもできません。少なくとも主体、テナント、リソース、操作を区別し、承認状態やポリシーバージョンに依存する場合は、キャッシュ設計や失効条件へ反映します。閲覧許可は承認許可ではなく、一つのレポートの結果を別のレポートへ使い回すこともできません。

ポリシーの集中管理は、毎回のリモート判断を意味しません。バージョンを付けて各サービスへ配布し、ローカルの業務データと組み合わせて評価する構成もあります。選択はルールの複雑さ、データの管理主体、一貫性の要件によります。

## 4. ローカル適用：具体的なリソースと操作を守る

レポートサービスはテナント、所有関係、ワークフロー状態に最も近い場所です。入口検査を通過しても、この利用者がこのレポートを読めるかを確認します。

次はメソッドセキュリティの例です。`#p0` は最初の引数を表します。

```java
@PreAuthorize("@reportPermission.canRead(authentication, #p0)")
public ReportDetail getReportDetail(Long reportId) {
    return reportService.getDetail(reportId);
}
```

重要なのは `canRead` の実装です。信頼できる認証コンテキストから利用者とテナントを取得し、正規の所有関係を照会して閲覧ルールを判断します。アノテーションだけで、この業務上の意味が自動的に補われるわけではありません。

Spring Security ではメソッドセキュリティを有効化し、呼び出しが対象プロキシを通ることも確認します。既定のプロキシ方式では、同じクラス内からの自己呼び出しがインターセプターを迂回する場合があります。保護されていないメソッドも、別の場所に認可アノテーションがあるだけでは安全になりません。一つの Controller の切り口だけでなく、到達可能な入口を確認します。

検索にも権限範囲を適用します。全レポートを取得してからフロントエンドで無権限の項目を隠す方式では不十分です。検索、ページ件数、エクスポートにも、テナントとデータ権限の条件が必要です。

承認などの書き込みでは、確認と実行の間に状態が変わることもあります。確認時には承認者でも、送信時には次の段階へ進んでいるかもしれません。フロー状態と承認資格が同じ業務 DB にあるなら、確認と更新を同じ原子的な処理の境界へ収めます。例えば適切なロック下で確認するか、関連する状態やバージョンを条件とする原子的な更新を行います。トランザクションを開始するだけでは競合はなくなりません。サービスをまたぐ状態に依存する場合は、別途調整の境界を明確にする必要があります。事前認可のアノテーションだけでは、実行時にも条件が成立する保証になりません。

ローカル適用は業務要求とともに認可処理を分散しますが、実際の負荷分散はトラフィック次第です。サービス間でルール定義を共有し、各入口を保護する必要もあります。

## 5. 権限失効：同期方式の前に反映時間を決める

「権限変更を即時反映する」は具体化が必要です。失効確認後に始まる要求を拒否するのか、すでに実行中の操作も止めるのか。プレビュー、エクスポート、承認送信では答えが異なり得ます。

通常の閲覧で短い反映時間を許容するなら、有効期間を限定したキャッシュとイベント失効を使えます。機密性の高い操作で、失効確認後の新規要求に古い権限を使わせないなら、判断経路で十分に新しい状態を読み取るか、その条件を満たすバージョン確認と同期的な確認応答が必要です。鮮度を確認できなければ実行を拒否します。短い TTL やキャッシュ更新通知だけでは、この動作を保証できません。

同期では、インスタンスの停止、通知の取りこぼし、到着順の逆転も考慮します。単調増加するポリシーバージョンで古い更新による上書きを防ぎ、起動・再接続時に最新版を取得し、定期照合で更新漏れを検出できます。

バージョン番号は差を検出する助けであり、全ノードを自動で同時切替する仕組みではありません。協調切替が必要なら、対象インスタンスの確認応答を待つか、未同期インスタンスによる対象要求の処理を制限します。一時的な不一致を認めるなら、その最大時間を決め、各インスタンスの遅れを監視します。

## 6. 三択ではなく責務を組み合わせる

三方式は着目する責務が異なります。

| 方式 | 主な責務 | 解決する問題 | 引き受けるコスト |
| --- | --- | --- | --- |
| ゲートウェイ検査 | トークンと基本ルート権限 | 早期拒否、入口ルール統一 | 業務文脈が限られ、遠隔照会で入口が遅くなる |
| 集中判断 | サービス間の共通ルール評価 | 権限モデルとポリシーの共有 | 通信依存、中心の容量、データ鮮度、判断キャッシュ |
| ローカル適用 | 業務データによるリソース・操作検査 | テナント分離、所有関係、フロー権限 | 検査の網羅性、ルール同期、実行との調整 |

このレポートシステムの例では、次のように組み合わせられます。

```text
要求
  → ゲートウェイ：トークンと閲覧・承認 Scope を確認
  → レポートサービス：認証コンテキスト、テナント、リソース、操作を確認
      ├─ ローカルの業務データと同期済みポリシー
      └─ 必要なら集中認可サービスへ照会
  → 有効な許可を得て閲覧・送信し、必要な監査情報を記録
```

まず権限粒度、失効反映時間、障害時の動作を決め、その後で遅延、スループット、可用性、維持コストを比較します。運用では認可の処理時間、遠隔判断のタイムアウト率、キャッシュ命中率、ポリシーバージョンの遅れを確認します。高い命中率が、古い権限の残存を伴う場合もあるため、一貫性の指標と合わせて判断します。

入口検査は共通に保ち、リソース権限は業務へ近づけ、共有ポリシーは一元的に維持できるようにします。管理、判断、適用の場所は別々に選べますが、その間の本人情報、データ、障害の境界を明確にする必要があります。
