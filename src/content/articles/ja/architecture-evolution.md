子会社は 2023 年 6 月に設立されました。私が 8 月に入社した当時、各案件が既存リポジトリを複製し、環境と相場プロバイダーへの接続を個別に管理していました。

当時契約していた Twelvedata、Finnhub の一部プランでは、API キーごとの WebSocket 接続が 1〜3 本に制限されていました。事業が規模化する前から、重複接続に月約 2,000 米ドルを費やしていました。これは当時の契約と接続方法における制約で、全商品に共通する固定値ではありません。

そこで RateHub を共通相場サービスとして設計しました。Twelvedata、Finnhub、Binance、Whitezzzs などに接続し、ETF、指数、株式、外国為替、現物、デリバティブの価格、板、複数周期のローソク足を提供します。

初版は接続と配信を分け、MongoDB で最新状態を共有しました。第 2 版は中核を一つのプロセスへ集約し、JVM メモリに最新価格を置き、上流のメッセージから直接配信します。重要な変更は、リアルタイムデータの流れです。

## 1. 初版：共有 DB で接続と配信をつなぐ

JDK 17、Spring Boot、MongoDB、Redis、Kafka、XXL-Job などを使用しました。

| 役割 | 主な責務 | 拡張の観点 |
| --- | --- | --- |
| Connect / 接続層 | 上流へ接続し MongoDB の価格を更新 | 上流接続と購読の規模 |
| Share / 配信層 | 認可と購読を管理し、価格を検索して WebSocket 配信 | 下流接続と送信負荷 |
| タスク | Redis / Redisson で調整してローソク足を処理 | 同じタスクの並行重複を抑える |

MongoDB の共有状態により、配信側は他インスタンスのメモリを読まずに接続側のデータを取得できました。

```text
上流 WebSocket → 接続サービス → MongoDB の最新価格
                                      ↓ 定期照会
                                  配信サービス → 下流 WebSocket
```

最新価格は銘柄ごとに上書きし、記録数を抑えました。ただし件数が少なくても、更新の DB 処理と照会・送信は続くため、I/O が小さいとは限りません。

キーには範囲も必要です。同名ペアでもプラットフォームや商品種別が異なります。ローソク足の識別にはデータ源、銘柄、周期、開始時刻が必要で、ペア文字列や時刻だけでは共有名前空間で区別できません。

Kafka は主に監視イベントとサービス間通知を扱いました。接続状態を管理サービスへ伝え、MongoDB へ保存して管理画面へ送ります。全価格の配信バスではなく、リアルタイム経路の DB 中継を置き換えてはいませんでした。

共有 DB はインスタンス別の状態調整を減らしますが、全読者が同時に同じ値を見る保証ではありません。読取時刻、構成、更新順序は依然として影響します。

## 2. 二つの負荷経路：相場 I/O と照会待機

一つ目は高頻度の読み書きです。接続側は更新し続け、配信側は利用者の購読ごとに照会するため、同じ価格を繰り返し読みます。

```text
価格更新 → DB 書き込み
             → 購読別に一回以上照会
             → 複数接続へ配信
```

読取負荷は相場量とクライアント数の両方に依存します。価格が変わらなくても定期照会や走査で I/O は発生します。低負荷時の高 I/O は、遅い検索、走査、タスク頻度を調べて原因を特定すべきで、MongoDB 固有の問題とは断定できません。

二つ目はローソク足の照会と補完です。上流 HTTP が遅いとプラットフォームスレッドが待機で占有され、接続プール、スレッドプール、キューへ要求が滞留し、他の要求にも影響します。

最新価格の DB 読み書き削減と、照会待機・並行数の制御は別々に必要です。サービス増設だけでは同じ DB や上流へ負荷を増やしかねません。

このサービスが必要としたのは最新スナップショットと一定頻度の更新で、全価格の再生ではありません。そのため最新状態を上流から再構築できます。全ティックの再生、監査、厳密な復元を求めるなら保存設計は変わります。

## 3. 第 2 版：リアルタイム経路を一つのプロセスへ

JDK 21、Spring Boot、Netty、MySQL、Redis、Kafka などを使い、接続、状態、購読、配信を独立配置できる一つのアプリへ集めました。DB とメッセージ基盤は外部に残ります。

上流コールバックは直接配信を起動し、最新スナップショットをメモリへ保持します。新規購読には既存スナップショットを返せます。

```text
上流 WebSocket → プロセス内の相場処理
                   ├─ 最新スナップショット更新
                   └─ 購読に応じて配信 → 下流 WebSocket
```

どちらも MongoDB への保存後に定期照会を待つ必要がありません。DB 中継と通信往復を減らすことで主要経路の仕事を削減します。遅延・処理量の効果は同条件の測定で確認する必要があります。

最新価格は「プラットフォーム + 銘柄」で保持します。複数源を接続しても、同名資産、通貨単位、契約定義が同じとは限りません。接続数を増やすだけでは自動切替にならず、銘柄対応、優先順位、鮮度、下流への通知を定める必要があります。

Redis は価格と板のスナップショットを定期保存し、再起動時に復元します。空白期間を短くしても、鮮度や全欠落更新の復元を保証しません。鮮度が重要な用途では、上流時刻とローカル受信時刻で期限を判断し、上流と再同期してから利用可能とします。

MySQL は銘柄・認可などの永続的な業務データを扱います。ローソク足は上流 API と Redis の期間キャッシュを使い、MySQL に完全な相場履歴があることを前提にしていません。

### Netty は接続モデルの選択であり容量保証ではない

Netty はイベント駆動の長期接続と非同期配信のために選びました。Tomcat の容量もプロトコル実装、設定、OS、業務処理に依存し、普遍的な WebSocket 上限で説明できません。

Netty のイベントループにも、遅い HTTP、ブロッキングロック、重い計算を入れるべきではありません。遅いクライアントは送信待ちデータを増やします。接続数、待機バイト、ループ遅延、消費速度を観測する必要があります。

最新価格だけが必要なら未送信スナップショットの統合を検討できます。一方、板の差分には順序や番号が重要な場合があり、同じ方式で捨てると完全スナップショットの再取得が必要になります。

## 4. ローソク足：キュー・キャッシュ・仮想スレッドの分担

WebSocket 照会は `socket-candlestick-topic` へ送り、コンシューマーが上流照会、キャッシュ、重複排除、検証、送信を行います。周期的なローソク足、ミニチャート、騰落率も、定期処理からメッセージを発行して実行します。

Kafka は遅い処理をイベント処理から移し、短期的な集中を吸収しますが、上流の利用枠は増やしません。到着量が処理能力を超え続ければ待機がキューへ移るだけです。送信側の待機動作も確認し、Kafka の利用だけでイベントループが非ブロッキングになると判断しないようにします。

周期タスクには仮想スレッドを使い、アンマウント可能な I/O 待機による占有を減らしました。JDK 21 には `synchronized` 内などの固定化もあり、全ブロッキングでキャリアが解放されるわけではありません。帯域、接続プール、上流枠も増えないため、実行中の要求数、タイムアウト、再試行間隔を制御します。

期間キャッシュを再利用して不足範囲を取得し、重複時刻と連続性を確認します。ただし正しさには次の条件が残ります。

- キーでデータ源、銘柄、周期を区別し、未確定足は更新可能にする。
- 休場と取引時間を考慮し、自然時間の空白すべてを欠損と見なさない。
- 週・月・年にはタイムゾーンと区切りを定め、すべて固定ミリ秒で扱わない。
- 始値・終値の補正には業務定義が必要で、実際のギャップを描画の連続性だけのために消さない。

これらがキャッシュで要求へ回答できるかを決め、最新価格と履歴の寿命管理が異なる理由にもなります。

## 5. キュー管理：意図と実装済みの能力を分ける

当時、規模が閾値を超えるとローソク足トピックを削除する定期処理を追加しました。しかし実装は分割のレプリカ数と同期レプリカ数を組み合わせており、メッセージ数や消費遅延を測っていません。信頼できる滞留保護が完成したとは言えません。

滞留には対象コンシューマーグループのコミット位置と分割末尾を比較し、最古タスクの待機時間も確認します。早期コミット後に非同期実行するなら、プロセス内の未完了処理も別に測定します。

トピック削除は未処理要求を失い、生産・消費側にも影響します。再試行可能な照会でも未完了をクライアントへ知らせる必要があり、通常の負荷平準化として削除を使うべきではありません。

期限切れ要求の拒否、流入と実行並行数の制限、重複照会の統合、再試行と失敗応答を定めるほうが制御しやすい方向です。WebSocket では要求 ID と有効な接続への対応も必要で、切断後の処理完了は結果が届いたことを意味しません。

## 6. 集約の効果と新しい境界

| 観点 | 初版 | 第 2 版 |
| --- | --- | --- |
| 最新価格 | MongoDB 更新と定期照会 | JVM 状態とコールバック配信 |
| 遅いタスク | スレッドを占有する同期呼び出し | Kafka 待機、周期処理は仮想スレッド |
| 再起動 | 共有保存先から読む | Redis 復元後に上流と再同期 |
| 主な代償 | 高頻度 DB I/O とサービス調整 | プロセス障害の影響、復旧、容量管理 |

単一プロセスは状態同期を減らす一方、一度の障害が接続と配信の両方へ影響します。Redis のスナップショットは WebSocket 接続を複製せず、二つのインスタンスの購読や送信状態を一致させません。複数を稼働させるなら、上流の割当、購読の所属、状態同期、再接続復旧が必要です。

分割の判断には鮮度、配信遅延、ループ遅延、送信滞留、メモリ、上流エラー、復旧時間を使います。可用性の目標によっては容量限界より先に冗長化と障害分離が必要です。

今回の集約は、リアルタイム経路に不要だった共有保存と定期照会を取り除きました。次の判断は独立拡張する部分、冗長化する状態、許容復旧時間に基づくべきです。これらを検証できることが、設計の価値になります。
