在要求租户隔离的报告系统中，一名用户即使持有有效的 Access Token，也具备报告读取 Scope，仍然不能随意访问另一家机构的报告。

如果他把请求中的报告 ID 换成其他租户的报告，而网关只检查令牌和 Scope，请求仍可能通过入口。判断它能否访问具体报告，还需要知道报告属于哪个租户、用户与报告有什么关系，以及当前允许哪些操作。

因此，资源鉴权的设计需要同时回答：谁管理规则，谁作出授权决策，谁负责执行，以及这些环节依赖的数据有多新。

下面以一个多租户报告系统为例，讨论网关入口鉴权、集中式授权决策和服务本地执行。三者可以组合使用。

## 一、先区分令牌校验、授权决策与权限执行

认证确认访问者是谁；令牌校验确认当前凭证是否可信；授权决策判断访问者能否操作某项资源；权限执行则负责在未获授权时真正阻止访问。

对于 JWT Access Token，资源服务器需要按配置验证签名、发行方、受众和时间约束，不能只解码后读取用户 ID。对于不透明令牌，则通常通过令牌内省或服务端状态查询判断其是否有效。

即使 JWT 校验通过，也不代表账号此刻仍然可用、权限尚未被撤销，更不代表用户能访问任意报告。令牌中的角色和 Scope 反映的是签发时的授权信息；是否需要查询当前状态，取决于业务允许多长的失效窗口。

Spring Authorization Server 提供 OAuth 授权服务器与 OpenID Connect 相关能力，包括授权流程和令牌签发。它与资源服务器承担不同职责，不能把它直接等同于“每次业务请求都要调用的权限服务”。

在报告系统中，可以先区分两类检查：入口判断请求是否具备进入报告服务的基本条件；业务服务判断用户是否能读取这份报告，或审批它当前所处的流程节点。

## 二、网关：尽早拦截，但不要替业务猜权限

网关适合完成通用、低成本的入口检查：验证令牌，按路由检查基础 Scope 或角色，并按需要执行黑白名单、限流及账号状态检查。这些能力可以在无效请求进入内部服务前将其拦截。

对于报告读取请求，网关可以要求调用方具备 `report:read` Scope。但报告的所属租户、归属关系和审批状态，通常仍由报告服务维护。如果网关为了判断具体资源权限，反复跨服务查询这些信息，就会承担越来越多的业务耦合与远程调用成本。

网关扩容只能增加网关自身的处理能力。如果瓶颈是共享的权限数据库或权限服务，增加网关实例甚至可能放大下游压力。此时需要先区分瓶颈来自令牌计算、远程查询，还是业务权限模型，而不是直接把扩容当作通用答案。

另一个容易被忽略的问题是身份如何传递。业务服务不能直接信任客户端提交的 `X-User-Id`、`X-Tenant-Id` 等请求头。若采用网关身份转发，必须移除或覆盖外部同名字段，并让服务能够验证身份信息的来源与完整性，例如通过经认证的内部通道或签名断言。

业务服务也可以重新校验适用于自身的访问令牌。无论选择哪种方式，都应明确可信入口；“请求来自内网”本身不足以证明身份可信。绕过网关的 RPC、内部接口和任务入口，同样需要适合其调用方式的身份与权限控制。

## 三、集中式决策：统一规则，同时承担远程依赖

当多个服务需要共享角色、组织关系或属性规则时，可以引入独立的权限服务或策略引擎。调用方提交主体、资源、操作及必要上下文，权限服务返回允许或拒绝，调用方据此执行。

例如，报告服务可以询问：“用户 A 能否审批租户 T 的报告 R？”其中租户、报告状态和审批关系，应来自可信身份上下文或权威业务数据，不能直接采信请求中自报的属性。

集中式决策有利于统一权限模型、复用规则和集中审计，但不会自动使数据保持最新：如果审批关系只缓存在权限服务中，仍要处理其更新与失效。将业务数据搬到中心服务，也会增加同步成本。

远程决策还会引入网络延迟和故障依赖。没有获得有效授权结果时，受保护的操作应默认拒绝。若允许复用已有缓存结果，就需要事先限定适用操作、有效期和撤销生效窗口，不能在超时后临时改为放行。

缓存键也不能只有用户 ID。针对某份报告的决定，至少需要区分主体、租户、资源和操作；如果决定依赖审批状态或策略版本，这些依赖也需要进入缓存设计或失效条件。读取被允许，不代表审批也被允许；一份报告的结果，也不能套用到另一份报告。

集中管理策略不等于每次请求都远程决策。规则可以统一维护、按版本发布到各服务，再结合本地业务数据执行。选择远程还是本地，取决于规则复杂度、数据归属与一致性要求。

## 四、服务本地执行：把权限落到具体资源与操作

业务服务最接近报告的所属租户、归属关系和流程状态，适合执行资源级权限判断。网关完成基础检查后，报告服务仍应确认“这名用户能否读取这份报告”。

下面是方法安全层的示意，`#p0` 表示第一个方法参数：

```java
@PreAuthorize("@reportPermission.canRead(authentication, #p0)")
public ReportDetail getReportDetail(Long reportId) {
    return reportService.getDetail(reportId);
}
```

这里的关键是 `canRead` 的实际实现。它需要从可信身份上下文获取用户与租户，查询报告的权威归属关系，并按规则判断读取权限。注解本身不会自动提供这些业务语义。

在 Spring Security 中，还需要启用方法安全，并确认调用经过相应代理。默认的代理模式下，同类自调用可能绕过拦截；未受保护的方法也不会因为项目里存在鉴权注解就自动安全。因此，应检查所有可达入口，而不是只给某个 Controller 加切面。

数据查询同样需要落实权限范围。报告列表不能先查询全部数据，再仅靠前端隐藏无权查看的条目；查询、分页计数和导出都应使用相应的租户与数据权限条件。

对于审批等写操作，还要考虑检查与执行之间的状态变化：检查时用户仍是审批人，提交时报告却可能已经进入下一节点。相关流程状态和审批资格如果存储在同一业务库中，需要把校验与更新纳入同一原子边界，例如在适当锁定后校验，或执行包含相关状态、版本条件的原子更新。仅开启事务并不自动消除竞态。若依赖跨服务状态，则还需要明确协调边界，单靠前置注解不能保证执行时条件仍然成立。

本地执行会让鉴权工作随业务请求分散，但负载是否均衡仍取决于实际流量。它也要求各服务使用一致的规则定义，并覆盖各自的访问入口。

## 五、权限撤销：先定义生效窗口，再选择同步机制

“权限变更立即生效”需要进一步澄清：是变更确认后的新请求必须拒绝，还是已经开始的操作也要终止？对报告预览、文件导出和审批提交，答案可能不同。

如果普通读取允许一个明确的短暂窗口，可以使用有界缓存和事件失效。如果敏感操作要求撤销确认后的新请求不得再使用旧权限，则必须在决策路径上读取足够新的授权状态，或使用能满足该约束的版本校验与同步确认机制；无法确认时拒绝执行。只缩短缓存 TTL，或发送一条“刷新缓存”通知，都不足以保证这一点。

策略同步也不能只考虑消息成功送达的情况。实例可能离线、错过通知，或收到乱序更新。可以为策略分配单调递增的版本，忽略旧版本覆盖；实例启动或重连时重新拉取当前版本，并通过周期性核对发现漏更。

版本号能够帮助识别差异，不能让所有节点自动同时生效。对于要求协调切换的策略，需要等待相关实例确认或限制未同步实例继续处理相应请求；如果允许短暂不一致，则应明确最长窗口，并监控各实例版本的落后情况。

## 六、如何组合，而不是三选一

三种方式关注的位置不同：

| 方式 | 主要职责 | 适合解决的问题 | 必须承担的代价 |
| --- | --- | --- | --- |
| 网关入口鉴权 | 令牌与基础路由权限检查 | 尽早拦截无效请求，统一入口规则 | 业务上下文有限，远程查询可能拖慢入口 |
| 集中式授权决策 | 跨服务规则的统一判断 | 共享权限模型与策略 | 网络依赖、中心容量、数据新鲜度与决策缓存 |
| 服务本地执行 | 结合业务数据检查资源与操作权限 | 租户隔离、资源归属、流程权限 | 检查覆盖、规则同步，以及检查与执行的协调 |

在这个报告系统的示例中，可以采用以下组合：

```text
请求
  → 网关：校验令牌与报告读取 / 审批 Scope
  → 报告服务：验证身份上下文，检查租户、资源与操作权限
      ├─ 本地业务数据 + 已同步策略
      └─ 必要时请求集中式权限服务
  → 获得有效授权后读取或提交，并记录必要的审计信息
```

选型时，先明确权限粒度、撤销生效窗口和故障时的处理要求，再比较额外延迟、吞吐、可用性与维护成本。上线后，应观察授权耗时、远程决策超时率、缓存命中率和策略版本落后情况；缓存命中率很高，也可能意味着权限变更迟迟没有生效，需要结合一致性指标判断。

合理的分工，是让入口检查保持通用，让资源权限靠近业务，让需要共享的策略能够统一维护。规则在哪里管理、决策在哪里计算、结果在哪里执行，可以分别选择，但它们之间的身份、数据与故障边界必须清楚。
